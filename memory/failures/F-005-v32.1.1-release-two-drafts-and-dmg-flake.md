# F-005  v32.1.1 release did not publish: two draft releases + macOS dmg flake
Status: FIXED-UNCONFIRMED      Severity: blocked
## 1. When (MST, with times)
- First reported by owner:      2026-10-13 13:54 MST (screenshots of the draft and the two failing checks)
- Release it appeared in:       v32.1.1 (merge commit 37879fed, tag pushed 2026-10-13 ~09:07 MST)
- Fix attempts (each with time, alpha, commit): (1) 2026-10-13 ~14:00 MST re-ran failed jobs only on run 38427906067: macOS went green, verify failed again. (2) 2026-10-13 ~14:30 MST PR fix/release-single-draft (this file).
- Confirmed fixed by owner at:  not yet
## 2. What the owner saw (exact words + screenshots, quoted)
- "the last release did not take for v32.1.1 as it failed in the mac release and immediately in the final check." Screenshots: a Draft release with only the Windows .exe; checks: Windows passed, macOS failed after 7m, Verify release assets failed after 3s.
## 3. What the owner expected
- v32.1.1 published with the Windows .exe and the Apple Silicon .dmg, like v32.1.0.
## 4. What actually happened (observed facts only, no guesses)
- Windows leg: success. macOS leg: tauri build compiled and signed the .app, then bundle_dmg.sh failed after about 7 seconds ("failed to run .../bundle_dmg.sh", no further detail). Verify job failed because no single release held both installers.
- After re-running only the failed jobs, the macOS leg passed and uploaded the .dmg and .app.tar.gz, but verify failed again after 6 seconds.
- GitHub then listed two separate draft releases, both named "BIG Hat Entertainment v32.1.1": id 411877036 with only BIG.Hat.Entertainment_32.1.1_x64-setup.exe, and id 412107070 with only the .dmg and the .app.tar.gz. No release had the tag v32.1.1.
## 5. Evidence (file names, line numbers, commands, outputs, git commits, measurements)
- Actions run 38427906067, macOS job 115402050145 log (bundle_dmg.sh error), verify job 115538028294 log ("Assets currently on release" lists only the .dmg and the .app.tar.gz).
- Release list API output with the two untagged drafts, created 16:02:15Z.
## 6. Root cause (state whether PROVEN or SUSPECTED, and how it was proven)
- Two causes. (a) Two drafts: PROVEN by the release list. Each matrix leg ran tauri-action with tagName and releaseDraft true, and each created its own draft. (b) The dmg failure: SUSPECTED runner flake in the disk-image step. Evidence: same workflow built the v32.1.0 dmg; a plain re-run of the macOS job succeeded; the log shows no code error.
## 7. Why it was not caught earlier (test gap, wrong bundle, no log, rule ignored, ...)
- The verify gate looked for a release by tag name, which never exists while the release is a draft. The v32.1.0 release only worked because the two legs happened to attach to one release. The release was tagged without checking the GitHub build afterwards.
## 8. Every fix attempt, in order: what was changed, why, result (worked / failed / unknown)
1. Re-run failed jobs: macOS worked, verify failed (two drafts). Did not fix the release.
2. PR fix/release-single-draft: new create-release job makes one draft first; both legs upload to it by releaseId; verify reads that release by id; the build step retries once. Result: unknown until the next tag.
## 9. What NOT to do again (also copy to DO_NOT_REPEAT.md)
- Never let two matrix legs each create the release. Never look up a draft release by tag name (drafts are listed as untagged-...). Never say a release is done before the verify job is green.
## 10. Test that proves the fix (name it) and proof the test can fail (what was broken on purpose)
- Only a real tag run can prove it. The workflow file was parsed with PyYAML (3 jobs, needs chain correct). Not run on GitHub yet.
## 11. Files touched
- .github/workflows/release.yml, this file.
## 12. Still unknown / open questions
- Whether tauri-action accepts releaseId with a draft that has no tag yet. Whether the draft can be published with the tag by the verify job (it only sets draft false). The cause of the dmg failure.
## 13. Owner impact (time lost, trust, data lost)
- v32.1.1 was not published for several hours. No data lost.
## 14. Process change made because of this
- Check the GitHub build after every tag and report the result; failures get a report in this folder.
